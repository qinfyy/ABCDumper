# NexusAnima 0.75.2 的 IL2CPP 与 Protobuf

## IL2CPP

- `GameAssembly.dll` 映像大小为 `0x935D000`。原生 type 指针表 `0x157CDB0` 的首项指向 RVA `0x1ED85C0`，其 `+8` 的 32 位值为 `0x001E0000`。运行时检查不匹配则拒绝绑定。
- `il2cpp_get_api_table` 在 `0x7F2D50`。程序集枚举 `0x7F4630` 写出 64 位计数；程序集转 image 为 `0x7F3F90`，image 名称为 `0x7F5BF0`，类数量和查找为 `0x7F5CA0`、`0x7F5CB0`。类方法迭代 `0x7F42D0` 使用 `Il2CppClass+0x40` 和 `+0x108`，不是嵌套类型迭代器 `0x7F4170`。
- `Il2CppClass::byval_arg` 在 `+0xA0`，实例大小在 `+0x106`。`MethodInfo` 的 invoker 在 `+0`，代码指针在 `+0x10`，参数数在 `+0x36`。`Il2CppType` 的 byref 是 `+0xB` 的 `0x20` 位；泛型实例指针在 `Il2CppGenericClass+8`。
- `FieldInfo` 步长为 `0x20`。偏移访问器 `0x7F4990` 使用低 24 位和 `0x5D4C1A` 解码；static/literal 从类型属性读取。枚举常量通过 `il2cpp_field_get_value_object` 读取，不沿用旧版默认值表。实例引用字段使用 `0x7F4A10`（`il2cpp_field_set_value_object`）：它用同一方式解码字段类型和实例偏移，并将对象引用直接传给类型分派 `0x7CE9E0`。

## Codec 识别与探测

- 匹配 static void 的完整签名：解析 `E4F51C817323798E(ref BF7236134CE913EC, ref T)`，写出 `AACD544EE3B749E4(ref EB1049810EFBEE36, T)`。任一签名存在即为 codec 候选；候选不等于网络消息。`E2107772BDBD37C2` 可用于筛选已知响应接口。候选包括 class 和 struct；解析时，前者的 `ref T` 是对象引用槽，后者是装箱对象的数据地址。
- 输入初始化 `0x4DCC4A0` 接收 16 字节 span 的地址和 128 字节上下文地址。输入当前位置是 `+0x10`；读尽后 `0x4E78480` 会清零当前位置并计入 `+0x20`，探针用两者之和核对消费量。输出上下文为 40 字节，span 长度在 `+8`，输出游标在 `+0x14`；本地探针只用固定容量的缓冲，耗尽分支 `0x4D48310` 在没有 backing writer 时抛出异常。
- 首先在新样本上执行 WriteTo 差分，再为剩余字段逐 tag 执行 MergeFrom。以实际变化为准，反汇编识别到的 tag 只用于调整探测顺序。单个 tag 触发的原生异常不会阻断其他字段的探测。
- 读端 tag 既可能通过比较链分派（例如 `0x4AEE389` 比较低字节），也可能经有界的相对跳表分派（例如 `0x4A08FF7`）。两种形式都只产生候选，需用对应样本验证。底层为 `uint` 的枚举在所有定义值均可用 proto3 的 int32 枚举表示时保留枚举类型。
- `Vector2`、`Vector3` 对应内联解析函数 `0x57E2B90`、`0x57E2DF0`，坐标使用内层 fixed32 线格式的 float 字段 `1/2[/3]`。`BAF18DA0E4BA6299`、`EFD1477E276EDDCA`、`E65F515F6EF69401` 分别对应 `0x57E1170`、`0x57E0F10`、`0x57E1AF0` 的 64 位整数内联结构。
- 数值集合用托管元素的实际位型匹配测试输入或输出。PooledList（`E13516D02DFE8FFC`）经 `+0x10` 取得 backing list，其数组和元素数分别在 `+0x18`、`+0x20`。仅有读端证据时标注 `packed: unverified`，不把可接受的 packed 输入当成写出形式。
- 混淆字典用 `+0x18` 的条目数组、`+0x20` 的计数及条目字段 `EF3AE79867E38521`、`B52E4FD9ECDC35A6` 核对键值。`A0593654DA2838C6` 字段 `20` 为字符串键、消息值，字段 `51` 为枚举键；`B4CE9F0460AAA61F` 字段 `1` 的内层键编号为 `2`。枚举键与编号反转都保留原始格式，写为嵌套 entry，而不是标准 `map`。不按托管字段声明顺序推断编号。
- 另一类字典没有 wire key。`0x57F4810` 等读端先解析 value，再调用 selector 计算键，最后插入字典。例如 `0x4F47C30` 从 value 的 `+0x28/+0x44` 组合出 `B49316AD85A4AB65<uint, uint>` 对应的键。用能填充这些成员的样本确认同线程、同输入的最外层读端命中该辅助函数且目标字典计数变化，导出为 `repeated Value`，不伪造 entry。若 value 带类型编号，则保留为 `repeated bytes`。普通 `map<uint32, ...>` 的 Spline 值不同：`0x57F2260` 分别读键和值，回调 `0x50A3EA0` 先经 `0x57E20E0` 读 wire surrogate `BBC8E29A09B175E6`，再在 `0x4C2D090` 转成托管 Spline。
- 存储类型和线格式类型可能不同。已确认先解析线格式 surrogate 再转换的样本：`B546EED8D77421A7` 对应 `B31EF4BAF2BD66C6`（`0x4C78270` → `0x4C78440`），`E39C2E654E9898C2` 对应 `E3903C2246C9FB25`（`0x4A55690` → `0x4A55820`），`ABC.Config.WwiseEvent` 对应 `B761E3FAB7979507`（`0x4F18E10` → `0x4C40EF0`）。`B23913127C7295DF<float/bool>` 按内联数据处理，以字段 `1` 表示存在性，字段 `2` 表示值。
- 读端注册表指针槽为 `0x2373B80`，其条目数组在对象 `+0x18`，entry 步长为 24 字节，索引键和 `MethodInfo*` 分别在 entry 的 `+8`、`+16`。观察实际分派并验证非空样本后，确认 `ABC.Config.GUID` 对应 `FCA86826C67FA44E`，`WwiseState` 对应 `B70E98D68A8553CE`，`WwiseSwitch` 对应 `FDDEB7B4F1D9A3E7`。这三种类型分别经过 `0x57E1040`、`0x57E1500`、`0x57E1630`。
- 部分长度分隔的载荷以原生 varint 类型编号开头，再跟所选类型的消息内容。例：`F4C491219275ABD4` 的字段 `3` 经 PooledList 辅助函数 `0x57E7420` 和元素回调 `0x50A6050`，最终分派于 `0x57E49B0`。只有样本实际经过此分派、被完整消费并改动对应成员时，才以 `bytes`（集合为 `repeated bytes`）保留原始载荷，不将前缀当成 protobuf tag。
- 类型编号能命中注册表不等于能插入集合。`E72A3A450655B846` 字段 `1` 的回调 `0x50A8BA0` 还要求结果可转换为 `A42F976BA3D90847`；`0x50A4EE0` 读到编号 `6` 时满足此条件，实测集合计数增加。
- `E82F7BEEB9366016` 和 `F24B983FE7999966` 的 `oneof` 读取分支分别在 `0x482BCB0`、`0x4485DA0`。同一输入修改值槽与嵌套判别枚举，且实际判别值和枚举常量均匹配 wire 字段号，才将值槽并入 `oneof`。读端异常单独标为 `PROBE ERROR`，不当作缺失字段。
- 空消息的读端可能只跳过未知字段，不分配对象。例如 `0x4C2BF90` 将空子消息的 null 结果写回相应成员。先为已确认的引用槽预置保活对象，再观察目标槽清空；仅消费完整不算证据。判别枚举和其他仅供托管逻辑使用的成员，在确认原生 codec 不单独访问或写出后标为 `MANAGED ONLY`。
- `EE19EBF758FECDAB` 的字段 `1` 是分隔长度的基类消息，不是独立引用槽。`0x4DE31CD` 将同一对象引用槽交给 `F2B222B133F8128E` 的读端；嵌套字符串样本只刷新基类 `+0x10` 的槽。导出用基类元数据名称表示嵌套消息，不把基类字段号平铺到子类。
- `A22A28CB2FA81B32` 经 `0x57E1C20` 读 `A73B7A34C961A4EC`，测试 payload 使用非零的内层 `BA2D4319492A453D`。 `F9C2B2206194B4EA` 经 `0x57E1890` 读 `BA8239ABE73BD9E5`，找不到标识时仍写入零，需在隔离样本中预置非零值以观察写入。 `ABC.Entity.CommonData` 经 `0x57E1760` 读 `BF6FB0A69F6EF564`，再由 `0x4D32A80` 转换。

## 整数编码与 XOR

- 一个探针不能区分 ZigZag 和 XOR。读端用多个不同长度的 varint 检查同一成员与数值模型是否给出相同掩码；写端用三个托管值比较同一 tag 和线格式。只有跨值一致且非零的掩码才输出 `XOR` 注释，覆盖 varint、fixed32 和 fixed64；浮点比较原始位型。
- `B80F42BB0FE468B8` 的解析函数 `0x4561E50` 读取 tag `0x48` 和 `0x60` 后，在 `0x4561FC7`、`0x4561F97` 执行 `xor eax, 0x8C6`。写出函数 `0x4561CC0` 在 `0x4561D2F`、`0x4561D8A` 写 varint 之前使用相同掩码。它作用于字段值，不是 tag 变换。相比之下，`B90642D8BB995086` 的字段 `3` 读写都符合 `sint32` 的 ZigZag 编码。
- packed 字段也可能把掩码作为参数传给辅助函数（`0x374C90`、`0x374A40`），不能只搜 codec 正文的 `xor immediate`。`EF2263570E40A9C4` 字段 `4` 已实测掩码 `0x982`。
- `XOR` 是对原生 codec 行为的记录，标准 protobuf 工具不会执行此变换。字典内层、间接调用和封包层的检查仍不完整，不能据此推断整包处理方式或认定掩码已找齐。

## 离线基准

`ABC.Common.dll` 的 `B62FCA9B447E245B` 实现响应接口。parse/write 分别在 `0x4863F30`、`0x4864110`，共享 invoker `0x590E00`。invoker 将参数槽 0/1 转为 RCX/RDX：parse 的参数 1 是引用槽，write 的参数 1 是对象。

| 2 | `FA85FD97955F3A2F` | `0x18` | `0x12` |
